# QR 文件传输工具 — 设计规格

日期：2026-10-17
状态：已获用户批准

## 1. 目标与场景

在完全内网、无 CDN、无外网的条件下，实现宿主机与隔离虚拟机之间的单向小文件传输：

- **发送端**：隔离虚拟机内，浏览器打开本页面，将文件编码为二维码序列在屏幕上循环播放。
- **接收端**：宿主机浏览器打开同一页面，通过 Screen Capture API（`getDisplayMedia`）抓取 VM 窗口画面，实时解码、重组文件并触发下载。
- 定位：**小文件**（几 KB 到几百 KB）。协议对小文件自动退化为单张静态二维码，对大文件自动切换为动态分片序列，一套代码兼容。

非目标（YAGNI）：加密（明文走屏幕，用户确认接受）、喷泉码、双向确认通道、手机扫码兼容。

## 2. 产物与结构

唯一产物：`qr-transfer.html`，单文件、零外部依赖、零构建步骤，四段式结构：

1. `<script>` 库区块 A：qrcode-generator（kazuhikoarase，字节模式，压缩后约 20KB）——原样内联，不维护
2. `<script>` 库区块 B：jsQR（纯 JS 无 wasm，压缩后约 90KB）——原样内联，不维护
3. `<style>` 界面样式
4. `<script>` 应用代码（协议 + 双模式 UI）

环境约束：

- 两端均为现代 Chrome/Edge。
- 接收端必须运行在**安全上下文**：`file://` 双击打开或 `localhost` 可用；**内网 `http://裸IP` 不可用**（`getDisplayMedia` 被浏览器拦截）。此限制写入页内使用说明。

模式选择：打开页面显示模式选择；`#send` / `#receive` 锚点直接进入对应模式（VM 内收藏 `#send` 书签固定为发送端）。`#test` 进入自测模式（见第 7 节）。

## 3. 协议

全部帧使用 QR **字节模式**（不走 base64，省 33% 体积）。每帧首字节为类型标记，第二字节为传输 ID `tid`（每次发送随机生成的 u8），接收端据此忽略上一次传输的残留帧。

### 3.1 头帧 `H`

```
[0x48][tid:u8][JSON UTF-8]
```

JSON 字段：`name`（文件名）、`size`（原始字节数）、`csize`（压缩后字节数）、`comp`（`"gzip"` | `"none"`）、`chunks`（分片数）、`sha256`（原始文件的 SHA-256，hex）。

### 3.2 数据帧 `D`

```
[0x44][tid:u8][seq:u16 LE][chunks:u16 LE][分片原始字节]
```

seq 上限 65535；按 600B/片可寻址约 39MB，远超定位。每帧携带分片总数 `chunks`，接收端无需等待头帧即可从循环任意位置开始预收集；头帧到达后补充文件名/哈希等元数据并校验完成。

### 3.3 整包帧 `A`（静态退化路径）

```
[0x41][tid:u8][jsonLen:u16 LE][JSON][全部数据]
```

当「压缩后全文 + 头 JSON」≤ 阈值（约 500B，默认分片容量内）时使用，单张静态 QR 完成传输。JSON 字段同 3.1，`chunks` 为 1。

### 3.4 播放与接收

- 播放序列：`H, D0, D1, …, Dn` 循环往复；整包帧则静止显示。
- 接收端可从循环任意位置加入：数据帧自带分片总数，未见到头帧时先预收集；头帧到达后保留已收分片并继续。重复帧丢弃；丢帧靠循环自然补回，无需喷泉码。

### 3.5 编码管线（发送）

文件 → ArrayBuffer → `CompressionStream('gzip')` 试压缩（变大则不压，`comp: "none"`）→ `crypto.subtle` 对**原始文件**算 SHA-256 → 切片 → 逐帧生成 QR。

解码管线（接收）为其逆序：收齐分片 → 拼接 → 解压（若 gzip）→ 校验 SHA-256 → Blob 触发下载。

## 4. 发送端 UI

- 拖放区 + 文件选择按钮。
- 控件：开始/暂停、帧率滑块（2–5 fps，默认 5）、分片大小选择（300/600/1000 B，默认 600）。
- 保活标记：页面左下角 6px 微型动画，持续制造画面变化，逼使窗口抓屏按帧率持续出帧（否则抓屏只在画面变化时出帧，可与发送帧率发生漏采混叠）。接收端帧签名忽略该边角区域。
- QR canvas：纠错级别 M，版本号自动适配数据量，模块像素随窗口自适应放大（含静区）。
- 状态区：文件名、当前帧 i/n、已循环圈数、每圈耗时。

吞吐估算：默认参数约 3KB/s，100KB 文件约 34 秒。

## 5. 接收端 UI

- 「开始抓屏」按钮（用户手势触发 `getDisplayMedia`，请求 30fps 理想帧率并设置 `contentHint='detail'` 保留细节），用户选中 VM 窗口；video 元素隐藏播放。
- 解码循环：`requestVideoFrameCallback` 跟随视频帧回调，并始终叠加 150ms 定时轮询（窗口被遮挡时 rVFC 可能不触发）。每次回调先算低分辨率帧签名（仅取画面中央 80%，忽略边角保活动画）。新画面按 80ms 最小间隔解码；同一画面解码成功过则跳过；解码失败则每 60ms 限速重试。解码画布长边等比缩至 ≤1600px，并关闭反色扫描。
- 状态机：`等待头帧 → 接收中（分片位图）→ 收齐 → 校验 SHA-256 → 解压 → 自动下载`。
- UI 元素：抓屏预览小窗、进度条 + 分片位图格子、文件信息、坏帧计数、抓屏/解码实时统计行（rVFC 帧率、轮询频率、画面变化、解码耗时，用于诊断漏帧）、完成后「重新下载」按钮、「重置」按钮。
- 诊断日志：控制台输出屏幕/窗口/DPR、抓屏设置与能力、视频→解码尺寸、每秒统计、每帧 seq 与缺失分片列表，用于定位丢帧发生在抓屏还是解码环节。

## 6. 错误处理

| 情况 | 行为 |
|---|---|
| 画面无二维码 | 提示「未检测到二维码，请确认发送端在播放且窗口未被遮挡」 |
| 解析失败 / 长度不符的帧 | 丢弃，坏帧计数 +1（辅助用户调整帧率/分片参数） |
| tid 不匹配的帧 | 静默忽略；接收中收到新 tid 的头帧则提示并重置 |
| 收齐但 SHA-256 不符 | 报错，继续接收（等待下一轮循环中的正确帧修复，可配合发送端重发） |
| 抓屏权限被拒 | 显示安全上下文说明（file://、localhost 可用；内网 http:// 不可用） |
| 分片超 65535 | 发送前拒绝并提示文件过大 |

## 7. 测试

- **`#test` 自测模式**：页面内运行编码→解码回环断言，包括：
  - 协议层：随机二进制数据切片→组帧→解析→重组→哈希比对（不渲染 QR）
  - 图像层：QR 渲染到 canvas 后经 jsQR 实际解码，验证端到端通路
  - 覆盖：小文件（A 帧路径）、多片文件（H/D 帧路径）、含 UTF-8 文件名、不可压缩数据（comp: "none"）
  - 不依赖抓屏，结果页内展示通过/失败明细
- **人工 E2E**：本机两个窗口互抓（发送窗口 + 接收窗口共享屏幕）。

## 8. 默认参数

| 参数 | 值 |
|---|---|
| QR 纠错级别 | M（15%） |
| 分片大小 | 600B（可选 300/1000） |
| 帧率 | 5 fps（可调 2–5） |
| 压缩 | gzip，能省才压 |
| 完整性校验 | 原始文件 SHA-256 |
| 整包帧阈值 | 约 500B |
