# QR 文件传输「补充模式」— 设计规格

日期：2026-10-19
状态：已获用户批准
前置设计：`2026-10-17-qr-file-transfer-design.md`

## 1. 背景与目标

现状：单向光学信道下丢帧只能靠发送端循环自然补回。文件几千帧时，漏几片也要多等一整圈（如 73 片 @5fps ≈ 15 s，几千片则达数分钟）。

目标：建立一条**人工反向信道**——接收端把缺失分片序号导出为紧凑文本，用户经任意通道（剪贴板共享、键盘手打）带回发送端，发送端**仅循环重发这些帧**，把补齐时间从「一整圈」压缩到「几秒」。

非目标（YAGNI）：

- 不引入 FEC(前向纠错)、喷泉码——与补充模式正交，未来可叠加
- 不做自动反向信道（架构上不存在）
- 不新增帧类型、不改协议字节格式
- 接收端 `Assembler` 零改动

## 2. 设计原则

1. **补发即重播**：补发循环播放的是原始帧对象（同一 `transfer`，tid、seq 不变）。接收端现有逻辑自动把补发帧当普通数据帧填入 `chunks[seq]`，收齐自动校验下载。
2. **头帧领衔补发循环**：序列为 `[H, …缺失数据帧…]`。头帧每圈触发接收端现有 `header-repeat` 分支（`qr-transfer.html` 的 `case 'header-repeat'`），Console 自动输出剩余缺失序号——每圈免费获得缺失报告，判断是否需要再补一轮。
3. **改动全部落在两端 UI 与两个纯函数**：缺失列表格式化（接收端用）、文本解析（发送端用）。

## 3. 用户操作流程

```
正常播放中接收端出现持续缺失
  ↓
① 发送端点「暂停」
② 接收端「复制缺失序号」→ 文本进剪贴板（文本框同时显示，可手动选择复制）
③ 用户经任意通道（剪贴板共享 / 手打）把文本带入发送端「补充模式」文本框
④ 点「仅补发这些帧」→ 循环播放 [头帧, …缺失数据帧…]（沿用当前 fps）
⑤ 接收端每圈头帧重复 → Console 自动报告剩余缺失；收齐 → 自动校验并下载
⑥ 仍缺 → 重复 ②–⑤；收齐后发送端手动暂停
```

## 4. 缺失序号文本格式

### 4.1 语法

```
#3-7,15,22-30;C9F27        ← 校验段数值为示意，实际按 4.2 计算
```

- **序号**：分片序号 `seq`（0 起，与接收端分片网格、`已收 x/y` 计数同口径）
- **区间**：`3-7` 闭区间；`-` 与 `~` 等价；`3-3` 合法（等价单片）
- **分隔符**（宽容）：中英文逗号 `,，`、中英文分号 `;；`、空格、换行
- **`#` 前缀**：可选，仅为视觉标识
- **校验段**：`;C` + 4 位大写 hex，仅当文本末尾匹配 `(?:;|；)[Cc][0-9a-fA-F]{4}$` 时识别为校验段

### 4.2 校验码定义

- 生成：对**去重升序后的缺失序号集合**逐个累积 `h = (h × 31 + seq) mod 65536`（h 初值 0），结果格式化为 4 位大写十六进制
- 采用位置加权而非简单求和：可拦截等和替换（如 `3,7` 误打成 `4,6`）与换位错误
- 验证对象 = **文本中成功解析出的全部序号（去重升序，含越界序号）**
- 规则自洽性：生成端不会产出越界序号，因此「校验相符」基本排除越界与错打；漏打/多打序号同样改变哈希被拦截
- **校验不符 → 拒绝启动补发**（红色提示）——手打防错底线
- **校验缺失 → 允许启动**，状态区提示「无校验码」

### 4.3 解析算法（发送端）

1. 去首尾空白；剥离可选的 `#`
2. 若文本末尾匹配校验段正则（4.1）则剥离并取出校验值
3. 主体按 `/[,，;；\s]+/` 分割；每段解析为 `a` 或 `a-b`/`a~b`（十进制，允许段内空白）；`a > b` 时交换；无法解析的段**计数忽略**
4. 序号集合去重升序；计算校验（规则同 4.2）并与文本校验段比对
5. 输出：`{ seqs, ignored, checksumOk: true|false|'absent', outOfRange }`
   - `outOfRange` = ≥ 当前 transfer `chunks` 的序号（仅无校验码时可能非空；有校验码时校验不符已拦截）
6. 结果为空集合 → 报错提示，不启动

## 5. 接收端改动

UI（分片网格 `#chunk-grid` 旁新增一行）：

- 只读文本框 `#missing-text`：实时显示当前缺失文本与缺失计数（如 `缺失 12 片：#3-5,7-15;C9F27`，校验值为实际计算结果）；既是 clipboard API 失败时的手动复制源，也是可视确认
- 按钮「复制缺失序号」：点击时快照计算 → `navigator.clipboard.writeText`；失败不报错，状态区提示「请从文本框手动复制」（`file://` 下页面失焦时 writeText 可能被拒）

行为：

- 可用条件：已知总片数（头帧已到，或数据帧预收集已建立 chunks 数组）；否则禁用并提示
- 缺失文本在每次分片状态变化时刷新（新收分片使列表缩短）
- 生成规则：遍历 `asm.chunks` 找 `null` → 天然升序 → 贪心合并连续段为区间 → 拼接 `#…;C…`
- 全部收齐后显示 `无缺失`
- `header-repeat` 每圈缺失日志为现有行为，不动

## 6. 发送端改动

UI（控件区下方新增「补充模式」区块）：

- 多行文本框 `#retry-input`（3–4 行高，支持粘贴长列表与手打短列表）
- 按钮「仅补发这些帧」`#btn-retry-start`、「恢复全量播放」`#btn-retry-full`
- 状态提示区：解析结果（`解析：12 片，忽略 2 段`）、校验状态、补发进度（`补发中：12 片｜第 2 圈｜每圈约 2.6 s`）
- 可用条件：`transfer` 已加载且为多帧（A 帧单帧路径禁用，tooltip 说明）

播放状态机：

- `sender` 新增 `mode: 'full' | 'retry'` 与 `playSeq: number[]`（帧索引序列）
- 全量模式 `playSeq = [0..n)`；补发模式 `playSeq = [0, …seqs.map(s => s + 1)]`（`+1` 跳过头帧占位）
- `start()` 与定时器回调改为按 `playSeq` 取帧；圈切换、圈耗时统计、fps、qrVersion、canvas 全部复用
- 「仅补发这些帧」：先 `pause()`，解析文本，校验通过后置 mode/序列并 `start()`
- 「恢复全量播放」：任意状态下置回全量序列并开始播放（等价于全量模式的开始）
- 任何时刻载入新文件：重置回全量模式，清空补发文本框

## 7. 边界与容错

| 场景 | 行为 |
|---|---|
| 单帧整包（A 帧） | 补发区块禁用 |
| 补发期间重播已收分片 | 无害，接收端去重（`chunks[seq] === null` 判断） |
| 接收端中途「重置」/刷新页面 | chunks 清空、缺失骤增，Console 日志可见；用户重新复制列表或回全量播放 |
| 发送端重新载入文件 | tid 变化，接收端整体 reset——补发仅对同一 transfer 有效，载入新文件即回全量模式 |
| 缺失超过全量一半 | 文本较长，不做强制拦截；解析结果显示片数，由用户判断是否改用全量 |
| 手打错误 | 校验码拦截（不符拒绝）；无校验码时坏段忽略并计数提示 |
| clipboard API 不可用 | 文本框常显文本，手动选择复制 |

## 8. 测试计划（`#test` 自测新增，现有 29 例不动）

1. **格式化**：`[3,4,5,7]` → `#3-5,7` + 按 4.2 定义计算的校验段（测试中以 `formatMissingSeqs` 输出比对，不手写死值）；连续、非连续、单片、全缺、无缺失各一例
2. **解析往返**：格式化 → 解析 → 同集合；分隔符变体（中英文逗号/分号、空格、换行）、`~` 区间、有无 `#`、有无校验段
3. **校验**：篡改一位序号 → 拒绝；删除校验段 → 放行且标记 absent；含越界序号且有校验 → 拒绝；无校验 → 越界忽略计数
4. **解析容错**：`a-b` 写反自动交换；坏段忽略计数；空文本报错
5. **补发序列构造**：`seqs=[3,7]`、frames 长 10 → `[0,4,8]`
6. **端到端（Assembler 级）**：构造多片 transfer → 模拟漏 3 片 feed 其余 → 断言未完成 → 以**原始帧字节** feed 补发的 3 帧 → 断言 `complete` 且数据 SHA-256 与源一致
7. **可用性判断**：提取纯函数 `canRetry(transfer)`——多帧 transfer 返回 true、A 帧单帧返回 false，UI 禁用状态由此驱动

命令行 `test/run-tests.sh` 自动覆盖（其运行 `#test` 页面）。

## 9. 代码组织

- 缺失文本格式化 / 解析两个纯函数：`__PIPELINE__` 区末尾（与重组逻辑同级，均为纯数据变换），命名 `formatMissingSeqs(seqs)` / `parseRetryList(text, chunks)`
- 接收端 UI 与刷新逻辑：`__RECEIVER__` 区
- 发送端状态机与 UI：`__SENDER__` 区
- 新增 DOM 与样式：与现有控件区风格一致
- 自测用例：`__TESTS__` 区追加
